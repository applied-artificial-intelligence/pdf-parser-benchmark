## Recent Decisions

### DOCX Pipeline Architecture

**Decision**: Use python-docx-template + LibreOffice instead of alternatives

**Rationale**:
- python-docx-template provides clean Jinja2 abstraction for DOCX
- LibreOffice headless is industry-standard for DOCX→PDF conversion
- Preserves complex formatting better than Python-only libraries
- Free, open-source, widely used in production

**Alternatives Considered**:
- Manual XML manipulation (rejected: too complex, error-prone)
- docx2pdf (rejected: Windows-only, requires MS Word)
- unoconv (rejected: deprecated, uses LibreOffice anyway)

### Ground Truth Extraction Strategy

**Decision**: Extract GT from rendered DOCX structure, not from template+context

**Rationale**:
- DOCX is source of truth after rendering
- Captures actual document structure
- Handles variable substitution correctly
- More accurate than reconstructing from context

**Implementation**: Parse DOCX XML, extract paragraphs with style detection, convert tables to GFM

### Test Data Quality

**Decision**: Create realistic, professional content for each template

**Rationale**:
- Tests template rendering with real-world complexity
- Provides meaningful content for visual inspection
- Ensures variable substitution works correctly
- Creates useful examples for documentation

**Examples**:
- Business report: Performance review language (14 vars)
- Financial report: Realistic numbers and structure (76 vars)
- Academic paper: Technical ML/NLP content (~30 vars)

### Diagnostic Labeling System

**Decision**: Label all tables in templates (TABLE-01, TABLE-02, etc.)

**Rationale** (from user feedback in previous session):
- Enables precise failure identification in benchmarks
- Allows parser capability mapping
- Facilitates targeted improvements
- Makes debugging and reporting more accurate

**Implementation**: Applied to both Pandoc (13 tables in 03_tables.md) and DOCX (5 tables in 02_table_heavy.docx)
